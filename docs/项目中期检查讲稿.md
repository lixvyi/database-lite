## 四、成员 A：SQL 编译器

成员 A 需要记住的主线：

```text
SQL → Token → AST → Semantic → Plan → Optimize
```

### 演示 A1：正常编译

#### 手敲 SQL

```sql
SELECT name FROM student WHERE age >= 18;
```

记忆：查询成年学生的名字。

#### 操作步骤

1. 进入 MiniDB 实验台。
2. 清空 SQL 输入框。
3. 手动输入上述 SQL，并检查末尾分号。
4. 点击“编译并检查”。
5. 依次点击 `Token`、`AST`、`语义` 和 `原计划`。

#### 展示 Token 时说

> 第一步是词法分析。Lexer 将完整 SQL 拆成 SELECT、name、FROM、student、WHERE、age、>=、18 和分号等 Token。
>
> 每个 Token 都保存类型、原文、值、行号和列号。例如 SELECT 是关键字，name 是标识符，18 是整数常量，>= 是运算符。保存行列号可以让系统准确定位错误。

#### 展示 AST 时说

> 第二步是语法分析。Parser 根据项目定义的 SQL 文法，把 Token 组合成 AST。
>
> 这条语句对应 SelectStmt。AST 中记录查询的表是 student，输出列是 name，WHERE 条件是 age 大于等于 18。Token 只是单词列表，而 AST 表示 SQL 的层次结构。

#### 展示语义时说

> 第三步是语义分析。SemanticAnalyzer 通过 Catalog 检查 student 表是否存在，name 和 age 列是否存在，以及 WHERE 后面的表达式是否能得到布尔值。这里显示 passed，表示检查通过。

#### 展示计划时说

> 语义检查通过后，系统生成执行计划。计划从下向上阅读：SeqScan 扫描 student 表，Filter 保留年龄大于等于 18 的记录，Project 最后只输出 name 列。

预期计划：

```text
Project
  Filter
    SeqScan
```

### 演示 A2：常量折叠优化

#### 手敲 SQL

```sql
SELECT name FROM student WHERE age > 10 + 8;
```

记忆：年龄大于十加八。

#### 操作步骤

1. 清空输入框并手动输入 SQL。
2. 点击“编译并检查”。
3. 点击“原计划”，指出 `10 + 8`。
4. 点击“优化后”，指出已经变成 `18`。

#### 现场讲稿

> 这里演示规则优化。10 加 8 与表中每一行的数据无关，因此不需要扫描每一行时重复计算。
>
> 优化器在执行前直接将它计算为 18，这叫常量折叠。优化只能改变执行方式，不能改变 SQL 的含义，所以优化前后的查询结果必须一致。

### 演示 A3：错误定位

时间充足时演示三类错误；时间不足时优先演示词法错误和语义错误。

#### 词法错误

```sql
SELECT @;
```

> 当前 SQL 子集不支持 @ 字符，所以 Lexer 报告 LexicalError，并给出第 1 行、第 8 列。错误在字符识别阶段被发现。

#### 语法错误

故意不输入分号：

```sql
SELECT name FROM student
```

> 这里每个单词都能识别，所以不是词法错误。但是项目文法要求语句以分号结束，因此 Parser 在输入末尾报告缺少分号。

#### 语义错误

```sql
SELECT x FROM student;
```

> 这条 SQL 的语法结构正确，但 student 表中不存在 x 列，因此 SemanticAnalyzer 报告列不存在。

#### 错误类型总结

```text
字符不能识别       → 词法错误
Token 排列不符合文法 → 语法错误
表、列或类型不正确   → 语义错误
```

### 成员 A 总结

> SQL 编译器已经完成关键字、标识符、整数、浮点数、字符串、运算符和分隔符的识别，支持大小写不敏感、单行和多行注释、字符串转义以及错误位置记录。
>
> 语法部分支持 CREATE、INSERT、SELECT、DELETE、WHERE 和常用表达式。SQL 编译器的两个扩展功能是 UPDATE 和 ORDER BY。我们没有继续增加 JOIN 和 GROUP BY，以保证一周内能够完整实现、测试并讲清楚。

## 五、成员 B：页式存储

成员 B 需要记住的主线：

```text
4KB Page → PageFile → PageCache → WAL → Checkpoint
```

### 演示 B1：分配页面

#### 操作步骤

1. 切换到 OS 存储仿真台。
2. 指向“页目录”，记住当前已分配页数量。
3. 点击“分配页”。
4. 观察已分配数量增加。
5. 指向新出现的深色页面格子。

#### 现场讲稿

> 我负责操作系统页式存储部分。底层数据文件被划分成固定大小的页面，每页是 4096 字节，每个页面都有唯一的 page_id。
>
> 点击分配页后，系统从页目录寻找空闲页。如果没有空闲页，就按照 64 页一个 Extent 扩展文件。
>
> 页面在文件中的偏移量等于 page_id 乘以 4096。例如第 2 页从文件偏移 8192 字节的位置开始。

### 演示 B2：修改内存页

#### 操作步骤

1. 点击“修改内存页”。
2. 观察 Buffer Frames。
3. 观察“缓存事件”。
4. 观察 WAL LSN 的变化。
5. 指出带红色外框的缓存页面。

网页没有页号和内容输入框。“修改内存页”会自动选择一个已分配页，并写入带时间的信息。

#### 现场讲稿

> 修改页面时，上层不会直接操作磁盘文件，而是先通过 PageCache 获取页面。
>
> 页面进入缓存后形成 Buffer Frame，其中保存 page_id、generation、dirty、pin_count 和 page_lsn。
>
> 页面修改后会被标记为 dirty，表示内存中的页面比磁盘更新。系统采用写前日志原则，先把修改记录到 WAL，只有日志已经持久化，对应脏页才允许写回磁盘。

### 演示 B3：Checkpoint

#### 操作步骤

1. 记住当前 WAL LSN。
2. 点击 `Checkpoint`。
3. 查看脏页数量是否变为 0。
4. 查看 Checkpoint LSN。
5. 查看缓存事件中的 `flush`。

#### 现场讲稿

> Checkpoint 会把可以安全写回的脏页刷新到磁盘，并记录当前一致点。
>
> 完成后 dirty 数量应该变成 0，Checkpoint LSN 会追上已经持久化的 WAL LSN。如果系统异常退出，重启时可以重放 Checkpoint 之后尚未写入数据文件的 WAL 记录。

### LRU 和 FIFO 说明

> 缓存支持 LRU 和 FIFO 两种替换策略。FIFO 优先淘汰最早进入缓存的页面；LRU 优先淘汰最久没有访问的页面。
>
> 页面被 pin 时表示正在使用，不能被淘汰。如果所有 Frame 都被 pin，系统会拒绝淘汰，避免覆盖正在使用的数据。

### 成员 B 总结

> 页式存储已经完成页分配、释放、读取、写入、页目录、缓存管理和脏页刷新。两个扩展是 64 页 Extent 分配，以及页级 redo WAL 和 Checkpoint。CRC 校验和双控制文件属于正确性保护，不作为额外扩展宣传。

## 六、成员 C：数据库引擎

成员 C 需要记住的主线：

```text
Plan → Executor → TableHeap → RecordCodec → SlottedPage
```

为了方便现场手敲，统一创建一张只有 `id` 和 `name` 两列的 `mid` 表。

### 演示 C1：创建表

```sql
CREATE TABLE mid(id INT,name VARCHAR(10));
```

#### 操作步骤

1. 返回 MiniDB 实验台。
2. 清空输入框并手动输入 SQL。
3. 点击“执行 SQL”。
4. 查看执行结果。

#### 现场讲稿

> 数据库引擎收到 CreateTable 计划后，在 Catalog 中登记 mid 表的结构。Catalog 记录表名、列名、类型和表的第一个数据页。系统目录也使用页式存储，而不是使用单独的 JSON 文件。

预期：

```text
table 'mid' created
```

如果提示表已经存在，可以将表名改成 `m2`，后续语句也全部使用 `m2`。

### 演示 C2：插入数据

```sql
INSERT INTO mid(id,name) VALUES(1,'A');
```

#### 操作步骤

1. 清空输入框并手动输入 SQL。
2. 点击“执行 SQL”。
3. 查看 `message`、`affected` 和 RID。

#### 现场讲稿

> INSERT 首先经过语义分析，检查 id 对应 INT，name 对应 VARCHAR。通过检查后，RecordCodec 把一行数据编码成字节，再写入 SlottedPage。
>
> 返回的 RID 由 page_id 和 slot_id 组成，分别表示记录所在的页面和槽位。

预期：

```text
1 row inserted
affected: 1
```

### 演示 C3：查询数据

```sql
SELECT * FROM mid;
```

#### 现场讲稿

> SELECT 生成 SeqScan 计划。执行器通过 Catalog 中的 first_page 找到表的第一页，然后沿页面链扫描记录。RecordCodec 将页面中的字节解码成行，最终返回查询结果。

预期：

```text
id: 1
name: A
```

### 演示 C4：UPDATE

```sql
UPDATE mid SET name='B' WHERE id=1;
```

执行后查询：

```sql
SELECT * FROM mid;
```

#### 现场讲稿

> UPDATE 先通过 SeqScan 和 Filter 找到 id 等于 1 的记录，再把 name 修改成 B。如果新记录可以放回原位置，就在原页更新；如果记录变长且空间不足，就插入新记录，再删除旧记录。

### 演示 C5：ORDER BY

```sql
SELECT name,age FROM student ORDER BY age DESC;
```

#### 现场讲稿

> ORDER BY 是我们选择的第二个 SQL 扩展。执行器先读取记录，再按照 age 降序排序，最后返回 name 和 age 两列。

### 演示 C6：DELETE

```sql
DELETE FROM mid WHERE id=1;
```

执行后查询：

```sql
SELECT * FROM mid;
```

#### 现场讲稿

> DELETE 找到目标记录后，把对应槽位标记为已删除。当前采用逻辑删除，不立即压缩整页，这样实现简单，RID 也更加稳定。页面压缩属于后续优化方向。

预期查询结果：

```text
rows: []
affected: 0
```

这里 SELECT 的 `affected: 0` 表示返回 0 行。

## 九、老师可能问的问题

### 1. 项目完成到什么程度？

> 三个模块的核心功能已经完成，并完成了从 SQL 输入到磁盘页持久化的整体联调。剩余工作主要是人工边界测试、文档完善和答辩准备。

### 2. 三个人如何分工？

> 成员 A 负责 SQL 编译器；成员 B 负责页式存储和缓存；成员 C 负责数据库引擎、接口和集成测试。三个人共同完成系统联调和验收测试。

### 3. 为什么只做这些扩展？

> 实训时间只有一周，我们优先保证基础功能正确、完整并且能够解释。扩展只选择与核心链路联系紧密、能够充分测试的功能。

### 4. 数据保存在哪里？

> 用户数据和系统目录都保存在 4KB 页面组成的 `tablespace.dat` 中。control 文件保存页目录和校验信息，`redo.wal` 保存页级重做日志。

### 5. 为什么项目中还有 SQLite？

> SQLite 只服务外围图书管理业务页面。课程验收使用的 MiniDB 实验台，从 SQL 编译、计划、执行器到页式存储都是自行实现的。

### 6. 如何证明项目不是只有界面？

> 实验台可以展示 Token、AST、语义结果、执行计划、页目录、Buffer Frame、WAL 和 Checkpoint，同时有 51 项自动测试验证底层行为。

### 7. 哪些功能没有实现？

> 当前没有实现 JOIN、GROUP BY、B+ 树索引、事务回滚、MVCC 和完整 SQL 标准。这是教学型小型数据库，不是生产级数据库。

说明浏览器没有连接到服务器。查看终端是否仍在运行；如果服务器已经停止，重新执行：

```powershell
python server.py
```

然后刷新网页。

### 2. 出现 `checksum mismatch`

说明旧演示数据损坏。停止服务器后执行：

```powershell
Remove-Item -Recurse -Force .\minidb_demo
Remove-Item -Recurse -Force .\os_sim_demo
python server.py
```

### 3. 提示 `table 'mid' already exists`

改用 `m2`：

```sql
CREATE TABLE m2(id INT,name VARCHAR(10));
```

后续 SQL 也全部使用 `m2`。

### 4. 提示缺少分号

在 SQL 末尾补充：

```text
;
```

### 5. 现场输入错误

可以直接说：
