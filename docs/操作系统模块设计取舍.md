# 操作系统仿真模块：为什么这样设计

## 1. 为什么做成独立实体

`os_sim.StorageService` 只暴露 PageStore 接口，SQL Parser 和 Executor 不知道文件名、缓存算法或 WAL 格式。这样数据库层可以测试逻辑，操作系统层可以单独做故障注入、缓存对比和并发压力测试。若把所有逻辑塞进 Executor，任何缓存或恢复改动都会污染 SQL 层，不符合 PPT 的模块边界。

## 2. 为什么一页 4096 字节

PPT 给出 4KB/8KB/16KB。项目选择 4KB，因为它与常见操作系统页大小一致，测试文件小，容易用十六进制工具核对 `page_id × 4096`。更大的页有更好顺序吞吐，但会放大只读一行时的读放大；教学项目更重视可观察性。

## 3. 为什么使用 Extent + allocation bitmap

方案比较：逐页增长实现简单但频繁扩展文件；空闲链表释放快但链损坏后恢复复杂；bitmap 可以直接回答页是否分配，且易持久化和检查。项目按 64 页 Extent 扩容，兼顾 PPT 的连续分配思想和代码可解释性。代价是首次扩容预留空间，属于有意的空间换时间。

## 4. 为什么控制文件保存两份

页目录和 checkpoint LSN 是“元元数据”。单份 JSON 在进程崩溃或写一半时可能无法启动，所以 `control.0.json` 与 `control.1.json` 都采用“临时文件 → fsync → 原子 replace”，启动时选 generation 最大的有效副本。这不是完整数据库控制文件，但明确仿真了多路复用。

## 5. 哪些放内存，哪些放磁盘

| 内容 | 内存 | 磁盘 | 原因 |
|---|---|---|---|
| 热数据页 | Buffer Pool | tablespace.dat | 内存加速，磁盘持久化 |
| pin/dirty/LRU 顺序 | 是 | 否 | 只描述当前进程状态，重启可重建 |
| 页目录/分配 bitmap | 热副本 | 双控制文件 | 启动必须知道哪些页有效 |
| redo WAL | 尾部缓冲极短 | redo.wal + fsync | 数据页前必须持久，保证恢复 |
| Catalog/业务记录 | 可缓存 | 数据页/目录 | 逻辑真相必须可恢复 |

## 6. 为什么默认 LRU，同时保留 FIFO

FIFO 只看进入顺序，O(1) 且最容易解释，但重复访问的热点页仍可能被淘汰。LRU 在命中时移动页，利用时间局部性，更适合交互式查询。两者共用同一 PageCache 接口和测试序列，能够证明差异，而不是只宣称 LRU 更好。当前默认 LRU；FIFO 用于课程对照实验。

## 7. 脏页何时刷回

三种时机均有明确理由：

1. 缓存淘汰：必须腾出 frame，脏 victim 先写回。
2. 脏页比例达到阈值：避免瞬间集中写盘。
3. Checkpoint/正常关闭：建立磁盘与 WAL 的一致恢复点。

不在每次修改后立刻写数据页，因为那会失去缓存合并多次修改的意义。修改时只同步 WAL；刷数据页前检查 `page_lsn <= durable_lsn`。这一 write-ahead 屏障保证不会出现数据页已落盘但恢复日志尚未落盘。

## 8. 服务器突然重启如何恢复

每次 `write_page` 先把完整页 after-image、generation、CRC 和 LSN 追加到 WAL 并 fsync，再把 frame 标脏。重启后从 `checkpoint_lsn` 之后顺序扫描 WAL；若磁盘页 generation 更旧，则重放新页。WAL 末尾若因断电只有半条 JSON，读取器停止于最后一条校验正确的记录。重放具有幂等性，因为 generation 不新的记录会跳过。

选择 redo after-image 而非 physiological log，是因为页面只有 4KB，教学代码更容易验证；代价是 WAL 较大。后续可改成 offset+delta。

## 9. 接口为什么以整页为单位

`allocate_page/release_page/read_page/write_page/checkpoint/stats` 与 PPT 的 I/O 最小单位一致。若接口直接暴露“写一行”，操作系统模块会知道 SQL Schema；若暴露文件 seek，数据库层又会绕过缓存/WAL。整页接口是两层最稳定、最小的边界。

## 10. 本阶段扩展边界

只选两项容易讲清的扩展：64 页 Extent 分配，以及页级 redo WAL + checkpoint。双控制文件与 CRC 是页文件正确性保护，不单独宣传为扩展。查询调度、B+ 树索引、Undo/MVCC 和代价优化留给后续阶段。
