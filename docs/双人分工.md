# 双人分工与接口边界

## 成员 A：SQL 编译器与查询优化

负责 `tokens.py`、`lexer.py`、`ast.py`、`parser.py`、`semantic.py`、`plan.py`、`optimizer.py`，以及 UPDATE/ORDER BY 的编译前端。

答辩必须掌握：字符如何推进并维护行列号；为什么文法没有左递归；NOT/AND/OR 如何体现优先级；AST 为什么不是 Token 堆叠；Catalog 如何完成名字绑定；类型错误在哪一层产生；SELECT 如何转换为 SeqScan→Filter→Sort→Project；常量折叠和布尔化简为什么等价。

## 成员 B：存储、执行、并发与权限

负责 `os_sim/`、`minidb/storage/`、`execution.py`、`catalog.py`、`auth.py`、`engine.py` 以及 Web API 集成。

答辩必须掌握：page_id 如何变成文件偏移；页 0 为什么是目录；页头、槽目录、空闲区和记录区如何增长；RID 如何定位一行；中文为何按 UTF-8 字节保存；WAL 障碍与脏页何时写回；LRU/FIFO 如何选择 victim；执行算子如何拉取行；表级读写锁与有界任务队列的边界；表/列/行/动作权限分别在哪一层判断。

## 共同责任

- 成员 A 为成员 B 提供稳定的 PlanNode；成员 B 不解析 SQL 文本。
- 成员 B 为成员 A 提供 Catalog 查询接口；成员 A 不读取物理数据页。
- 两人共同确认文法、端到端协议、隐藏测试、现场修改和失败分析。

## GitHub 协作

- `main` 只接收通过测试的版本。
- 使用 `feature/compiler-*` 与 `feature/storage-*` 分支，PR 由另一人审阅。
- 每次提交只跨一个模块边界；示例：`feat(parser): support NOT precedence`。
- Issues 分别记录需求、反例、测试和答辩问题，不只上传最终压缩包。
